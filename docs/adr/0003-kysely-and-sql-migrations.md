# 0003. DB アクセスは Kysely + SQL マイグレーション（Prisma は使わない）

- ステータス: 採用
- 日付: 2026-10-11
- 経緯: 当初の指示は Prisma だったが、「性能改善のため、Prisma より SQL を実行したい。より良いものがあれば別でよい」との要望を受けて変更した

## 背景

X のタイムライン、通知、検索、集計は、複数テーブルの JOIN・集計・並び替えが中心で、性能がサービスの体験を左右する。
そのため「発行される SQL を自分で設計し、読めて、チューニングできる」ことを重視する。

## 検討した選択肢

1. **Prisma** — 開発が速く型も安全。ただし発行される SQL が見えにくく、複雑なクエリ（ウィンドウ関数、CTE、LATERAL JOIN など）は生 SQL に逃げることが多い。関連の取得で N+1 を作りやすい
2. **生の SQL（pg / postgres.js）のみ** — 完全に制御できる。ただし型が付かず、タイポや型のズレに実行時まで気づけない
3. **Drizzle** — SQL に近く型安全。スキーマを TypeScript で定義する流儀で、マイグレーションの SQL は自動生成が中心
4. **Kysely + SQL ファイルのマイグレーション + kysely-codegen** — SQL そのままの感覚で書けて型も付く。スキーマの正は SQL（マイグレーション）で、型は実 DB から自動生成する

## 決定

**選択肢 4** を採用する。

- クエリは **Kysely**（型安全な SQL ビルダー）。複雑な部分は `sql` テンプレートで生 SQL も書ける
- スキーマ変更は **素の SQL ファイル**（`packages/db/migrations/`、node-pg-migrate）。インデックスやパーティションなどの DB 固有の機能を自由に使える
- 型は **kysely-codegen** が実 DB から `packages/db/src/generated/` に自動生成する（手で編集しない）
- 値は必ずパラメータ化する（SQL インジェクション対策）

## 結果

- 良い点: SQL を直接チューニングできる。`EXPLAIN` の結果とコードが 1 対 1 で対応する。型安全性も保てる
- 注意点:
  - 「マイグレーション → `pnpm db:codegen`」の手順が必須（忘れると型エラー。hook が通知する）
  - 関連のロードを自動でしてくれる機能はないので、JOIN を自分で書く（N+1 を作らないこと）
  - 適用済みマイグレーションは編集しない（hook でブロック）
