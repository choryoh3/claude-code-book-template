# 0008. shared と ui パッケージの設計と、ライブラリの選び方

- ステータス: 採用
- 日付: 2026-10-11

## 背景

Phase 2 で、画面（client）とサーバー（server）が共有する `packages/shared`（API 契約）と、`packages/ui`（見た目の部品）を作った。
作る際に、「ビルドは要るか」「どのライブラリを使うか」「契約をどう守るか」を決める必要があった。

## 決定

### 1. ビルドせず、TypeScript のソースをそのまま共有する

`@xclone/shared` と `@xclone/ui` は、ビルド（`dist` への出力）をせず、`package.json` の `exports` が `./src/index.ts` を直接指す。

- 理由: アプリ側の Vite / tsx が TypeScript をそのまま読めるため、ビルド手順が不要になり、変更がすぐ反映される。設定ファイルと待ち時間が減る
- 注意: 将来、パッケージを外部に公開するならビルドが必要になる（今は社内の部品なので不要）

### 2. 契約は Zod 4 を唯一の真実にする（`packages/shared`）

- 型は `z.infer` で導出し、手書きの interface と二重管理しない（`.claude/rules/shared-contracts.md`）
- エラーメッセージは日本語で、画面にそのまま表示できる文言にする（`messages.ts`。画面仕様書のメッセージ一覧と一致させる）
- 日時は ISO 8601 の文字列で受け渡す（JSON に載せるため）
- 一覧は 2 種類: ユーザー向けは cursor 方式（無限スクロールで件数が増えても速い）、管理画面は page 方式（「◯ページ目へ移動」が必要なため）

### 3. DB の列挙型と shared の定数の一致を、型で保証する

`packages/db/src/contract.ts` で、DB の自動生成型と shared の定数を比較する。食い違うと `pnpm typecheck` が失敗する（わざと食い違わせて、検出できることを確認済み）。
「DB の enum に値を足したのに shared に足し忘れた」というバグを、実行前に防ぐため。

### 4. UI ライブラリ

| 用途                 | 採用                                      | 理由                                                                                                  |
| -------------------- | ----------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| アクセシビリティ部品 | **radix-vue**（指定どおり）               | Esc で閉じる・フォーカスの閉じ込めなどを自前で作らずに済む。npm 上で非推奨にはなっていない            |
| アイコン             | **@lucide/vue**（指定は lucide-vue-next） | `lucide-vue-next` は npm 上で「非推奨。`@lucide/vue` を使うこと」と表示されているため、後継を採用した |
| クラスの合成         | clsx + tailwind-merge（`cn()`）           | 外から渡した class で、同じ種類のクラスを上書きできる                                                 |
| バリアント           | class-variance-authority（`cva`）         | 見た目の種類（primary / danger など）を型つきで定義できる                                             |
| テスト               | Vitest + Vue Test Utils + happy-dom       | 軽く、ブラウザ無しでコンポーネントの動作を確認できる                                                  |

**見直しの条件**: radix-vue の後継は **Reka UI（`reka-ui`）** で、同じ作者による Vue 向けの継続版。radix-vue の更新が止まる、または新機能が必要になったら、`reka-ui` へ移行する（import 元の名前が変わる程度で、部品の使い方はほぼ同じ）。

## 結果

- 良い点: ビルド不要で軽い。契約が 1 か所にまとまり、DB・画面・サーバーのズレを型とテストで防げる
- 注意点: `shared` を変えたら、使っている全てのアプリの型チェックとテストを通すこと（`pnpm check`）
