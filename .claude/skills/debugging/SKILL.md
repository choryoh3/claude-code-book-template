# 不具合調査の手順

**推測で直さない。再現 → 観察 → 原因特定 → 修正 → 回帰テスト** の順で進める。

## 1. 再現する

- 症状を「期待」と「実際」に分けて書く。エラー文言・画面・操作・時刻を控える
- 最小の再現手順を作る。テストデータ（`docs/test-data.md`）のアカウントを使う
- 再現できないときは、環境差（`.env`、DB の状態、マイグレーション未適用）を疑う

## 2. 観察する（証拠を集める）

| 見るもの      | 方法                                                                                                                                                      |
| ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| サーバーログ  | `logs/user-server.log` / `logs/admin-server.log`（1 行 1 JSON）。`pnpm logs:errors` で直近のエラー、`pnpm logs:trace <requestId>` で 1 リクエストの全ログ |
| HTTP の応答   | レスポンスの `error.code` と `requestId`（エラー応答に必ず含まれる）                                                                                      |
| DB の実データ | postgres MCP（読み取り）。制約・インデックス・`EXPLAIN (ANALYZE, BUFFERS)`                                                                                |
| 画面          | Playwright MCP でスクリーンショット・コンソールエラー・失敗リクエスト                                                                                     |
| 変更履歴      | `git log -p -- <file>` / `git blame`。直近の変更が原因でないか                                                                                            |

ログの読み方: `requestId` が同じ行を時系列に並べ、**最初のエラー**と**その直前の処理**を見る。

## 3. 原因を特定する

- 仮説を立て、**反証できる確認**で絞り込む（ログを足す、条件を変えて再実行、SQL を直接実行）
- 症状ではなく根本原因まで掘る（「null だった」→「なぜ null になったか」）
- 確信が持てない場合は、確信度を明示し、追加で必要な情報を挙げる

## 4. 直す

- 根本原因を直す。症状を隠すだけの `try/catch` や `?.` は足さない
- **先に失敗するテストを書く**（回帰テスト）→ 直す → 通ることを確認する
- 原因が設計上の落とし穴なら、`docs/troubleshooting.md` に症状・原因・対処を追記する

## 5. 報告する

症状 / 根本原因（根拠つき）/ 修正内容 / 追加したテスト / 再発防止策、の順で簡潔に報告する。
